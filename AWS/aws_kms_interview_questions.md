# AWS KMS Interview Questions

## Basic Questions
1. What is AWS KMS?
    - Answer: AWS Key Management Service (KMS) is a managed service that makes it easy to create and control the cryptographic keys used to encrypt your data. It provides centralized key management and integrates with other AWS services.

1. What are the main use cases for AWS KMS?
    - Answer: Common use cases include data encryption, protecting sensitive data, managing encryption keys, and integrating with services like S3, RDS, and Redshift to encrypt data at rest and in transit.

1. How does AWS KMS handle key storage?
    - Answer: AWS KMS securely stores keys within a hardware security module (HSM) to ensure high availability and durability, while also offering features like automatic key rotation.

1. What types of keys can you create in AWS KMS?
    - Answer: You can create customer-managed keys (CMKs), which are keys that you create and manage, and AWS-managed keys, which are keys created and managed by AWS for use with specific services.

1. What is a customer-managed key (CMK)?
    - Answer: A customer-managed key (CMK) is a key that you create and control in AWS KMS. You can define permissions, manage key rotation, and specify how the key can be used.

1. What is a data encryption key (DEK) in AWS KMS?
    - Answer: A data encryption key (DEK) is a key used to encrypt data. It is typically generated by KMS, encrypted with a CMK, and then stored or used to encrypt sensitive data.

1. What is the difference between symmetric and asymmetric keys in KMS?
    - Answer: Symmetric keys use the same key for encryption and decryption, while asymmetric keys use a public key for encryption and a private key for decryption. AWS KMS supports both types.

1. What is an AWS-managed key?
    - Answer: An AWS-managed key is created and managed by AWS for use with specific AWS services. Users do not have direct control over these keys, as they are automatically managed by AWS.

1. Can you use KMS keys across different AWS regions?
    - Answer: No, **KMS keys are region-specific**. Keys created in one region cannot be used in another region.

1. What is a key policy in AWS KMS?
    - Answer: A key policy is a resource-based policy that defines who can use a KMS key and what actions they can perform. It is attached directly to the CMK.
        - Like IAM Policies, Key Policies are 'deny by default', meaning access is implicitly denied.
        - Key Policies are **mandatory** for all KMS keys, The default policy for a new key is:
            ```
            {
            "Sid": "Enable IAM User Permissions",
            "Effect": "Allow",
            "Principal": {
                "AWS": "arn:aws:iam::111122223333:root"
            },
            "Action": "kms:*",
            "Resource": "*"
            }
            ```
            - This does **not** grant the root user of your AWS account automatic access to everything. Instead, it safely delegates authorization controls to the account's IAM system.
            - Once this statement is active, any IAM user or role inside account `111122223333` that has an attached IAM policy allowing `kms:Decrypt` or `kms:Encrypt` will be allowed to use the key.
            - : If you delete this block from your key policy, all standard IAM policies granting access to this key will become useless. Only the specific users or roles explicitly named in your custom KMS key policy statements will retain access.

1. How can you grant permissions to use KMS keys?
    - Answer: Permissions can be granted using key policies, IAM policies, or resource-based policies that specify which users or roles can use the keys and what actions they can perform.

1. How can you rotate keys in AWS KMS?
    - Answer: You can enable automatic key rotation for customer-managed keys, which rotates the key once per year, or you can manually create new keys and update references in your applications.

1. What is a key alias in AWS KMS?
    - Answer: A key alias is a friendly name that you can assign to a KMS key to make it easier to reference. It is a way to simplify key management without exposing the key ID.

1. How do you delete a KMS key?
    - Answer: KMS keys can be scheduled for deletion. You can specify a waiting period of 7 to 30 days before the key is permanently deleted. During this period, the key cannot be used.

1. What happens to data encrypted with a key that is deleted?
    - Answer: If a key is deleted, **any data encrypted with that key becomes unrecoverable** and cannot be decrypted.

1. What is a grant in AWS KMS?
    - Answer: A grant is a method of providing specific permissions to a principal (user, group, or role) for a KMS key. It is a way to give temporary access without modifying key policies.

1. How can you audit KMS key usage?
    - Answer: You can audit KMS key usage through AWS CloudTrail, which logs all API calls made to KMS, including key creation, usage, and deletion events.

1. What is the difference between a key policy and a grant?
    - Answer: A key policy defines access permissions for a KMS key and is attached to the key itself, while a grant provides temporary access permissions to a specific principal without modifying the key policy.

1. How does AWS KMS integrate with AWS Organizations?
    - Answer: AWS KMS allows you to create and manage keys across multiple AWS accounts within an organization, enabling centralized key management and policy enforcement.

1. How do you encrypt data using AWS KMS?
    - Answer: Data can be encrypted by calling the Encrypt API operation, which uses a KMS key to encrypt the plaintext data and returns the encrypted data along with the key metadata.

1. What is envelope encryption in AWS KMS?
    - Answer: Envelope encryption is a technique that uses a DEK to encrypt data, which is then itself encrypted with a CMK. This method improves security and efficiency, especially for large datasets.

1. Can you use AWS KMS to encrypt data in transit?
    - Answer: While KMS is primarily used for **encrypting data at rest**, you can use it to encrypt data in transit by integrating it with other services that support TLS/SSL for secure data transmission.

1. What is the process of decrypting data using AWS KMS?
    - Answer: Decryption is done by calling the Decrypt API operation with the encrypted data, and KMS uses the associated CMK to return the decrypted plaintext.

1. What are the best practices for using AWS KMS?
    - Answer: Best practices include:
        - Using IAM policies and key policies to enforce least privilege.
        - Enabling automatic key rotation.
        - Auditing key usage with CloudTrail.
        - Implementing envelope encryption for sensitive data.

1. How can you enforce data encryption in an AWS account?
    - Answer: You can enforce data encryption by using IAM policies that require encryption for specific services and integrating KMS with those services to ensure data is encrypted at rest.

1. What are some AWS services that can be integrated with AWS KMS for encryption?
    - Answer: AWS services that integrate with KMS include Amazon S3, Amazon RDS, Amazon EBS, AWS Lambda, Amazon Redshift, and Amazon EFS, among others.

1. How does AWS KMS handle key access in a multi-tenant environment?
    - Answer: AWS KMS isolates key usage across different AWS accounts and tenants through IAM and key policies, ensuring that only authorized users and applications can access specific keys.

1. What is the role of AWS Identity and Access Management (IAM) in KMS?
    - Answer: IAM roles and policies are used to control who can access and manage KMS keys, allowing you to enforce security and compliance across your AWS environment.

1. How does AWS KMS affect application performance?
    - Answer: AWS KMS incurs some latency due to network calls for encryption and decryption operations. Optimizing key usage and minimizing API calls can help mitigate performance impacts.

1. What are the cost components associated with AWS KMS?
    - Answer: Costs associated with AWS KMS include:
        - Charges for each API request (Encrypt, Decrypt, etc.).
        - Charges for key storage (per key per month).
        - Additional costs for using KMS with other AWS services.

1. How can you minimize costs when using AWS KMS?
    - Answer: Costs can be minimized by optimizing the frequency of API calls, leveraging grants for temporary access instead of key policies, and evaluating the need for multiple keys.

1. What factors can influence the performance of KMS operations?
    - Answer: Factors include network latency, the complexity of data being processed, and the configuration of the KMS service itself. High request rates may also lead to throttling.

1. How do you monitor the performance of KMS keys?
    - Answer: Performance can be monitored using AWS CloudWatch metrics and logs, which provide insights into API usage and operational metrics for KMS keys.

1. What is a HSM, and how does it relate to AWS KMS?
    - Answer: A Hardware Security Module (HSM) is a physical device used to manage digital keys securely. AWS KMS uses HSMs to protect the cryptographic keys used for encryption and decryption.

1. What is the significance of key rotation in AWS KMS?
    - Answer: Key rotation helps maintain security by periodically changing encryption keys, reducing the risk of key compromise and ensuring compliance with best practices.

1. How can you implement multi-factor authentication (MFA) for KMS operations?
    - Answer: MFA can be enforced by creating IAM policies that require MFA for KMS actions, adding an additional layer of security when accessing or managing keys.

1. What are KMS data protection mechanisms?
    - Answer: Data protection mechanisms include encryption at rest, data integrity checks, access control through key policies, and auditing capabilities using CloudTrail.

1. How does AWS KMS support the use of custom key stores?
    - Answer: Custom key stores allow you to manage your own keys using HSMs outside AWS, while still integrating with AWS KMS for encryption services.

1. What is the significance of using HSM-backed keys in AWS KMS?
    - Answer: HSM-backed keys provide additional security by ensuring that cryptographic operations occur within secure hardware modules, helping to meet regulatory compliance requirements.

1. How does AWS KMS support compliance with PCI DSS?
    - Answer: AWS KMS helps meet PCI DSS compliance by providing secure key management practices, including encryption of sensitive cardholder data and robust access controls.

1. What are some key considerations for using AWS KMS in a multi-account environment?
    - Answer: Key considerations include setting up cross-account access using resource-based policies, ensuring proper IAM role permissions, and managing key aliases for clarity.

1. How can you implement logging and monitoring for AWS KMS keys?
    - Answer: Logging can be implemented using AWS CloudTrail to capture API calls, while AWS CloudWatch can monitor metrics related to key usage and send alerts for unusual activity.

1. What are some potential vulnerabilities when using AWS KMS?
    - Answer: Potential vulnerabilities include improper key policies, excessive permissions granted through IAM, and failure to monitor key usage and access patterns effectively.

1. How do you manage costs associated with AWS KMS?
    - Answer: Costs can be managed by optimizing the number of API calls, leveraging grants for temporary access, and monitoring usage patterns to eliminate unnecessary expenses.

1. What is the cost structure for using AWS KMS?
    - Answer: The cost structure includes charges for each KMS API call (Encrypt, Decrypt, etc.), monthly storage fees for keys, and any additional costs associated with HSM-backed keys.

1. How can you analyze the cost impact of using KMS in your architecture?
    - Answer: You can analyze costs by using AWS Cost Explorer to monitor KMS usage, reviewing detailed billing reports, and identifying high-frequency API calls that contribute to costs.

1. What strategies can you employ to reduce KMS usage charges?
    - Answer: Strategies include consolidating API calls, using caching for DEKs, and ensuring efficient key rotation policies to minimize unnecessary key operations.

1. What steps would you take if a KMS key is not accessible?
    - Answer: Check IAM policies, verify key policies, review CloudTrail logs for access attempts, and **ensure that the key has not been scheduled for deletion**.

1. How can you respond to an unauthorized access alert related to KMS keys?
    - Answer: Investigate the access attempt using CloudTrail logs, revoke any compromised permissions, and conduct a review of key policies to enhance security.

1. How can you recover from a deleted KMS key?
    - Answer: If a KMS key is deleted, **recovery is not possible**. Ensure that you have backup strategies for encrypted data and avoid deleting keys unless absolutely necessary.

## Scenario-Based Questions
1. You enabled encryption on your S3 bucket. Why did you choose 'SSE-KMS' (Customer Managed Key) instead of the default 'SSE-S3' (AWS Managed Key)?
    - The Answer: We chose SSE-KMS with a Customer Managed Key (CMK) for Control and Auditing.
    - SSE-S3: It's easy, but AWS owns the key. I cannot see who used the key to decrypt a file, and I cannot share that key with a partner's AWS account.
    - SSE-KMS (CMK):
        - Audit: I can check CloudTrail to see exactly which user decrypted which file (critical for compliance like GDPR/HIPAA).
        - Control: I can rotate the key on my schedule or revoke access immediately if a user is compromised, without deleting the data.

1. What happens if you accidentally delete the KMS Key used to encrypt your 10TB Data Lake?
    - The Answer: If the key is permanently deleted, the data is Cryptographically Shredded.
    - The Reality: The data files still exist in S3, but they are just random noise. Without the key, it is mathematically impossible to retrieve the data.
    - The Safety Net: **AWS does not let you delete a key instantly.** You must schedule deletion (minimum 7 days, default 30 days). During this window, we can cancel the deletion and restore access.

1. I have `AdministratorAccess` (IAM). I tried to download a file encrypted with a Custom KMS Key, but I got `Access Denied`. Why?
    - The Answer: This is the unique property of KMS: Key Policies are King.
    - The Rule: Unlike S3 or EC2, where IAM Admin access usually overrides everything, for KMS, **the Key Policy is the primary source of truth**.
    - The Scenario: If the Key Policy explicitly says 'Only the DataEngineeringRole can use this key', then even the Root User or an Admin cannot use it unless they are added to that policy.
    - The Fix: I need to look up the Key ID, go to the KMS Console, and add my IAM User/Role to the 'Key Users' list in the Key Policy.

1. We need to copy data from a Production Account (Source) to a Lower Environment (Destination) for testing. The data is encrypted. How do we allow the Destination account to read it?
    - The Answer: This requires a Three-Step Handshake for Cross-Account KMS access:
        1. Source Key Policy: Update the Production KMS Key Policy to trust the Destination Account ID (Principal).
        1. Destination IAM Policy: Update the IAM Role in the Destination Account to allow `kms:Decrypt` on the Source Key ARN.
        1. The Copy: The Destination user runs the CopyObject command. They decrypt using the Source Key and re-encrypt using the Destination Key.

1. Why don't we send our 1GB CSV file to KMS to encrypt it directly? Explain 'Envelope Encryption'.
    - The Answer: KMS has a payload limit (4KB). It is not designed to encrypt data; it is designed to encrypt keys. We use Envelope Encryption:
    - Data Key: When writing a file, the SDK asks KMS for a 'Data Key'.
    - Encryption: We use the plaintext Data Key to encrypt the 1GB file locally (on the EC2/Lambda) using AES-256. This is fast and efficient.
    - Storage: We store the Encrypted Data Key alongside the file. We discard the plaintext key.
    - Why: This avoids sending massive data over the network to KMS, preventing network bottlenecks and latency.

1. You are using Kinesis Firehose to ingest data. You encrypted the stream. Suddenly, Firehose stops writing to S3. Logs show KMS.`ThrottlingException`. What happened?
    - The Answer: We hit the KMS API Request Limit.
    - The Scenario: Every time Firehose writes a batch, it calls KMS to decrypt/encrypt data keys. If traffic spikes to 10,000 records/sec, we might exceed the default limit (e.g., 1,000 or 5,000 requests/sec).
    - The Fix:
    - Data Key Caching: Use the AWS Encryption SDK or client-side caching to reuse Data Keys for a short period (e.g., 1 minute) instead of calling KMS for every single object.
    - Quota Increase: Request a Service Quota increase for KMS cryptographic operations.

1. We enabled 'Automatic Key Rotation' for our KMS Key. Does this mean we have to re-encrypt all our 5 Petabytes of historical data in S3?
    - The Answer: No, thankfully.
    - How it works: When AWS rotates a key, it generates a new 'Backing Key' (Version 2). New data is encrypted with Version 2.
    - Decryption: AWS keeps Version 1 (and all older versions) active essentially forever. When you try to read an old file, KMS checks the metadata, sees it was encrypted with Version 1, and uses Version 1 to decrypt it transparently.
    - Re-encryption: You only need to re-encrypt old data if you explicitly want to move it to the new key version for compliance reasons, but it is not required for access.

 

1. We have a Disaster Recovery (DR) requirement. If us-east-1 goes down, we failover to eu-west-1. Can we use the same KMS Key ID in both regions so our application code doesn't change?
    - The Answer: Standard KMS Keys are Regional. **They cannot leave the region they were created in.**
    - The Solution: We must use KMS Multi-Region Keys.
    - How it works:
        1. Create a Primary Key in us-east-1.
        1. Replicate it to eu-west-1.
        1. Both keys share the same Key ID and key material.
    - Benefit: If you copy an encrypted backup from East to West, the application in West can decrypt it immediately using the local Replica Key without any code changes or re-encryption steps.

1. A Developer committed an encrypted secret to Git. He says 'It's safe, it's encrypted with KMS'. Is he right?
    - The Answer: It is safe from the public, but dangerous for the company.
    - Why: If the Git repo is public, anyone can see the encrypted string. They cannot decrypt it unless they have access to your AWS account and the KMS Key.
    - The Risk: If a hacker gains access to an IAM Role in your account (e.g., via a leaked Access Key), they can download that Git repo and use your own KMS key to decrypt the secret.
    - Best Practice: **Never commit secrets, even encrypted ones.** Use Secrets Manager or strictly control who has `kms:Decrypt` permissions.

1. You are configuring encryption for a Data Lake. You see options for 'Symmetric' and 'Asymmetric' KMS keys. Which one do you choose and why?
    - The Answer: For S3 and most AWS data services, we always use Symmetric Keys.
    - Symmetric (AES-256): The same key is used to encrypt and decrypt. This is what AWS services (S3, EBS, RDS) support natively because it is fast and efficient.
    - Asymmetric (RSA/ECC): Uses a Public/Private pair. This is used for Digital Signatures or when you need to share a Public key with a 3rd party partner so they can encrypt data outside AWS that only you can decrypt. It is not supported for standard S3 bucket encryption.

1. You created a KMS key policy that allows `kms:Decrypt` for your User. You try to download a file from S3, and it works. You try to run a Lambda that downloads the file, and it fails with `AccessDenied`, even though the Lambda has the exact same IAM permissions as you.
    - The Answer: The Key Policy likely has a `kms:ViaService` condition.
    - The Logic: A Key Policy can restrict how the key is used.
    - Condition: `{ StringEquals: { kms:ViaService: s3.us-east-1.amazonaws.com } }`
    - The Failure: If the Lambda tries to call KMS directly (or via a different service not listed), the condition fails.
    - The Fix: Ensure the Key Policy allows the specific service principal (Lambda or the service the Lambda is invoking) to use the key.

1. To satisfy a strict bank regulation, you used Bring Your Own Key (BYOK). You generated key material on an on-premise HSM and imported it into KMS. One year later, at 3:00 AM, your entire production database goes down. It cannot decrypt anything. The KMS Key ID still exists in the console.
    - The Answer: Your imported key material Expired.
    - The difference:
        - AWS Managed Key Material: Never expires. AWS rotates it seamlessly.
        - Imported Key Material: When you import it, you can set an expiration date (or it might have been deleted/rotated incorrectly on the import side).
    - The Danger: If imported material expires or is deleted, the KMS Key container (shell) remains, but it is empty. It cannot decrypt anything.
    - The Fix: You must re-import the exact same key material (same bits) from your offline backup immediately. If you lost that backup, the data is lost forever.

## Error-Based Questions
1. You have full Admin access (`AdministratorAccess`) in IAM. You try to decrypt a file using a Customer Managed Key, but you get `AccessDeniedException`. How is this possible?
    - The Answer: KMS is unique because **IAM permissions are not enough**.
    - The Concept: KMS uses Key Policies as the primary source of truth. Even if I am an Admin, if the Key Policy explicitly says 'Only the ETL-Role can use this key', then I cannot use it.
    - The Fix: I must look up the Key ID, go to the KMS Console (if I have permission to view keys), and add my IAM User/Role to the 'Key Users' list in the Key Policy.

1. You are trying to encrypt a 100MB CSV file using the `kms.encrypt` API call in Python. It fails with an error. Why?
    - The Answer: KMS APIs have a hard limit of 4KB for direct encryption.
    - The Error: You cannot send large data to KMS. KMS is designed to encrypt keys, not data.
    - The Fix: Use Envelope Encryption.
        1. Call `kms.generate_data_key()`. KMS returns a plaintext key and an encrypted key.
        1. Use the plaintext key to encrypt the 100MB file locally (using a library like OpenSSL or Python's cryptography).
        1. Store the encrypted data key alongside the file in S3.

 

1. Your ETL job fails with `InvalidCiphertextException` when trying to decrypt a secret, even though the key ID is correct. What is the likely cause?
    - The Answer: This usually happens due to an Encryption Context Mismatch.
    - The Logic: When you encrypt data, you can pass an optional dictionary called 'Encryption Context' (e.g., {'Project': 'DataLake'}).
    - The Trap: If you provided a context during Encryption, you MUST provide the exact same context during Decryption. If you omit it or change even one character, KMS treats the ciphertext as invalid/tampered and refuses to decrypt it.
    - The Fix: Check the code that encrypted the data and ensure the decryption call includes the identical EncryptionContext parameter.

1. We need to copy an encrypted S3 object from Account A (Prod) to Account B (Dev). The copy command fails with `AccessDenied`. We already updated the Bucket Policy. What is missing?
    - The Answer: For encrypted objects, you need to open Two Doors: The S3 Door and the KMS Door.
    - The Missing Piece: The Destination Account (Account B) needs permission to `kms:Decrypt` using the Source Account's (Account A) KMS Key.
    - The Fix:
        1. Source KMS Key Policy: Update the Key Policy in Account A to allow the IAM Role in Account B to use the key.
        1. Destination IAM Policy: Update the IAM Role in Account B to allow `kms:Decrypt` on Account A's Key ARN.
        1. The Copy: Account B performs the copy. It decrypts with Key A and re-encrypts with Key B (Dev Key) during the write.


1. Your high-volume Kinesis Firehose stream is writing to S3. Suddenly, it stops writing, and you see `ThrottlingException` errors in the logs. You checked S3, and it's fine. What is happening?
    - The Answer: You are hitting the KMS API Request Limit.
    - The Scenario: Every time Firehose writes a batch of files, it calls KMS to generate or decrypt data keys. If your stream volume spikes (e.g., 5,000 requests/sec), you might exceed the default KMS quota (which varies by region, e.g., 1,200 or 5,500 RPS).
    - The Fix:
        - Data Key Caching: Ensure the producer uses the AWS Encryption SDK with Data Key Caching enabled (reusing the data key for 1 minute instead of requesting a new one for every record).
        - Quota Increase: Submit a Service Quota Increase request for KMS Cryptographic Operations.

1. You enabled 'Automatic Key Rotation' for your KMS key. Do you need to update your application code to handle the new key version?
    - The Answer: No, the rotation is transparent.
    - How it works: AWS generates a new 'Backing Key' (HBK) but keeps the old ones active.
    - Decryption: When your app tries to decrypt a file encrypted 2 years ago, KMS sees the metadata, knows it was encrypted with 'Version 1', and transparently uses Version 1 to decrypt it.
    - Encryption: New data is encrypted with the current 'Version 2'.
    - The catch: You generally do not need to re-encrypt old data manually unless you have a strict compliance requirement to retire old backing keys completely.

1. You have a Multi-Region architecture (US-East and EU-West). S3 Replication is enabled. If US-East goes down, how do you ensure the replicated data in EU-West can be decrypted immediately without reconfiguration?
    - The Answer: You must use KMS Multi-Region Keys (MRK).
    - The Problem with Standard Keys: Standard KMS keys are regional. Key ID 123 in US-East is totally different from Key ID 123 in EU-West. S3 Replication re-encrypts data at the destination, usually requiring a different key config.
    - The Fix: Create a Multi-Region Key.
        - This shares the same Key ID and Key Material across regions.
        - If US-East fails, the application in EU-West can simply call `kms:Decrypt` using the same Key ID it uses in US-East, and it will work against the local EU-West replica of the key.

1. You manage a Production KMS Key. You log in Monday morning and see the key state is `PendingDeletion`. All ETL jobs are failing. Who did this, and can you save the data?
    - The Answer: First, **Cancel the Deletion immediately**.
    - The Mechanism: **KMS keys are never deleted instantly.** There is a mandatory waiting period (7 to 30 days). During this time, the key state is `PendingDeletion`, and it cannot be used for cryptographic operations (hence the ETL failure).
    - The Fix:
        - Call `kms:CancelKeyDeletion` (via CLI or Console) to revert the state to Enabled. The ETL jobs will start working again instantly.
        - Investigation: Use CloudTrail to search for the event `ScheduleKeyDeletion` to identify the user or automated script that triggered the deletion.

1. You encrypted your RDS snapshots using the Default KMS Key (aws/rds). You are trying to share this snapshot with a different AWS account (e.g., for analytics in the Data Lake account). The 'Share' button is greyed out, or the other account cannot see the snapshot. Why?
    - The Answer: You cannot share Default (AWS Managed) Keys.
    - The Constraint: Keys like aws/rds, aws/s3, or aws/ebs are managed by AWS. Their Key Policies are read-only and restrict usage strictly to the account that owns them. You cannot grant cross-account access to them.
    - The Fix:
        1. Copy the snapshot in the source account.
        1. During the copy, re-encrypt it using a Customer Managed Key (CMK).
        1. Share the CMK-encrypted copy with the target account.

1. You have a long-running EMR cluster. Suddenly, it fails to launch new Spark executors. The error logs show: `LimitExceededException` related to KMS. You check the API Request Quota (TPS), and it's low. What other limit did you hit?
    - The Answer: You hit the Grant Limit per Key.
    - The Logic: EMR uses KMS Grants to delegate permission to EC2 instances dynamically. Every time a node starts or a user submits a job, EMR might create a new Grant.
    - The Limit: A single KMS key can support up to 50,000 Grants by default. If your cluster is very dynamic or older clusters didn't clean up properly, 'zombie grants' pile up.
    - The Fix:
        1. Immediate: Audit and revoke unused grants using `kms:ListGrants` and `kms:RevokeGrant`.
        1. Long-term: Configure EMR to use fewer keys or ensure the EMR Service Role has proper permissions to RetireGrant upon cluster termination.

1. You have a Lambda function that decrypts data. The IAM Role allows `kms:Decrypt` on the key TargetKey. A malicious developer changes the code to try and decrypt a different secret (encrypted with the same TargetKey but intended for a different app). How does Encryption Context prevent this access?
    - The Answer: Encryption Context acts as Non-Secret Authentication Data (AAD).
    - The Mechanism: When we encrypt the sensitive secret, we tag it with {App: Payroll}.
    - The Attack: The malicious Lambda tries to decrypt the 'Payroll' secret. Even though it has the Key permissions, if the code doesn't pass `{App: Payroll}` in the decrypt call, KMS rejects it.
    - The Policy: Crucially, we restrict the Lambda's IAM policy with a Condition: `Condition: {StringEquals: { kms:EncryptionContext:App: Frontend }}`. Now, the Lambda physically cannot ask KMS to decrypt anything labeled 'Payroll.
