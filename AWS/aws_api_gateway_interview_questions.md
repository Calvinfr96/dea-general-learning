# AWS API Gateway Interview Questions

## Basic Questions
1. What is AWS API Gateway?
    - Answer: AWS API Gateway is a fully managed service that enables developers to create, publish, maintain, monitor, and secure APIs at any scale.

1. What are the key components of API Gateway?
    - Answer: Key components include APIs, resources, methods, stages, and usage plans.

1. What types of APIs can be created using API Gateway?
    - Answer: You can create REST APIs, HTTP APIs, and WebSocket APIs using AWS API Gateway.

1. How does API Gateway integrate with AWS Lambda?
    - Answer: API Gateway can invoke AWS Lambda functions directly as backend services to handle requests, allowing for serverless architectures.

1. What is a resource in the context of API Gateway?
    - Answer: A resource is an entity within the API that can be accessed via a URL path and typically corresponds to a specific object or action in the application.

1. What is the difference between a stage and a deployment in API Gateway?
    - Answer: A deployment is a snapshot of your API configuration at a point in time, while a stage represents a specific environment (e.g., development, testing, production) for that deployment.

1. How do you manage API versioning in API Gateway?
    - Answer: API versioning can be managed through path parameters, query string parameters, or by creating different stages for each version of the API.

1. What is a method in API Gateway?
    - Answer: A method is an operation (GET, POST, PUT, DELETE) that is associated with a resource and defines how clients can interact with that resource.

1. How can you secure your APIs in API Gateway?
    - Answer: APIs can be secured using IAM roles and policies, API keys, Lambda authorizers, and AWS Cognito for user authentication.

1. How can you monitor API Gateway usage?
    - Answer: You can monitor usage using Amazon CloudWatch metrics, enabling you to track requests, latency, and error rates.

1. What logging capabilities does API Gateway provide?
    - Answer: API Gateway allows you to enable detailed logging of requests and responses, including request/response bodies and headers.

1. How do you implement error handling in API Gateway?
    - Answer: Error handling can be implemented by configuring custom error responses and mapping error codes to user-friendly messages.

1. How do you analyze logs generated by API Gateway?
    - Answer: Logs can be analyzed using Amazon CloudWatch Logs Insights, which provides a query language for searching and visualizing log data.

1. What are the common backend integrations supported by API Gateway?
    - Answer: Common integrations include AWS Lambda, HTTP endpoints, AWS services (e.g., DynamoDB), and Mock integrations for testing.

1. What is a Mock Integration in API Gateway?
    - Answer: A Mock Integration simulates responses from an API without needing a backend service, useful for testing and development.

1. Can API Gateway invoke other AWS services?
    - Answer: Yes, API Gateway can invoke other AWS services directly through AWS service integrations.

1. How do you set up CORS in API Gateway?
    - Answer: CORS can be configured in API Gateway by enabling it on the method settings and specifying allowed origins, methods, and headers.

1. What is the purpose of API keys in API Gateway?
    - Answer: API keys are used to identify and control access to your APIs, enabling usage tracking and throttling for specific consumers.

1. How do you use AWS Cognito with API Gateway?
    - Answer: AWS Cognito can be used to provide user authentication and authorization by configuring it as an authorizer in API Gateway.

1. What are Lambda authorizers?
    - Answer: Lambda authorizers are custom Lambda functions that validate access tokens or API keys before granting access to APIs.

1. How can you restrict access to certain API methods?
    - Answer: Access can be restricted using IAM policies, API keys, or Lambda authorizers based on user roles and permissions.

1. What is the role of AWS WAF with API Gateway?
    - Answer: AWS Web Application Firewall (WAF) can be used with API Gateway to protect APIs from common web exploits and mitigate security risks.

1. What techniques can be used to improve the performance of APIs in API Gateway?
    - Answer: Performance can be improved through caching responses, optimizing payload sizes, and minimizing backend latency.

1. How does caching work in API Gateway?
    - Answer: Caching stores the response of a method for a specified duration, reducing the number of requests made to the backend and improving response times.

1. What are the default limits in API Gateway regarding requests per second?
    - Answer: The default limit is 10,000 requests per second, but this can be increased by requesting a service limit increase from AWS.

1. How can you achieve high availability with API Gateway?
    - Answer: High availability can be achieved by deploying APIs across multiple regions and using CloudFront for content delivery.

1. What is the significance of response size limits in API Gateway?
    - Answer: API Gateway has response size limits (6 MB for payload) which impact the amount of data returned to the client and may require pagination or data reduction.

1. What is the difference between REST API and HTTP API in API Gateway?
    - Answer: REST APIs offer more features and capabilities, while HTTP APIs provide a simpler, lower-cost alternative optimized for HTTP traffic.

1. What are custom domain names in API Gateway?
    - Answer: Custom domain names allow you to use your domain name instead of the default API Gateway domain, providing a branded URL for your APIs.

1. What are some common issues you might encounter with API Gateway?
    - Answer: Common issues include latency problems, throttling errors, authentication failures, and integration errors with backend services.

1. How do you troubleshoot API Gateway request failures?
    - Answer: Troubleshooting involves reviewing CloudWatch logs, checking integration settings, and verifying API configurations.

1. What should you do if you encounter throttling errors in API Gateway?
    - Answer: If throttling errors occur, consider adjusting usage plans, increasing API limits, or optimizing backend performance.

1. How can you validate the input to your API?
    - Answer: Input validation can be achieved using request validation settings in API Gateway, which checks for required parameters and data types.

1. What steps can you take to handle unexpected errors in API Gateway?
    - Answer: Implement custom error responses, log errors in CloudWatch, and return user-friendly messages to clients.

1. How do you ensure compliance when using API Gateway?
    - Answer: Compliance can be ensured by implementing security best practices, auditing access logs, and adhering to data privacy regulations.

1. How do you handle sensitive data in API Gateway?
    - Answer: Sensitive data should be encrypted in transit (using HTTPS) and at rest, and access should be restricted using IAM roles and policies.

1. What is throttling and how does it work in API Gateway?
    - Answer: Throttling limits the number of requests to APIs to prevent overload, helping maintain performance and availability.

1. What is the importance of API Gateway response times in performance testing?
    - Answer: Response times are critical for user experience; long response times can lead to user dissatisfaction and increased abandonment rates.

1. What is the significance of HTTP status codes in API Gateway?

    - Answer: HTTP status codes indicate the result of API requests, providing clients with information on success, redirection, client errors, or server errors.

1. Describe a scenario where API Gateway would be useful in a data pipeline.
    - Answer: API Gateway can serve as the endpoint for receiving real-time data from sensors or applications, which can then trigger processing workflows via AWS Lambda.

1. How can you use API Gateway to create an event-driven architecture?
    - Answer: API Gateway can receive events from various sources and trigger AWS Lambda functions or other services, enabling asynchronous processing.

1. Can you provide an example of using API Gateway for an e-commerce application?
    - Answer: In an e-commerce application, API Gateway can handle product catalog requests, manage user sessions, and process orders via different backend services.

1. What is the role of API Gateway in a serverless architecture?
    - Answer: API Gateway acts as the front door for serverless applications, managing API requests and integrating with AWS Lambda and other services.

1. How do you handle API deprecation in API Gateway?
    - Answer: API deprecation can be handled by notifying users, providing a migration path to the new version, and maintaining backward compatibility as much as possible.

1. What are the security best practices for API Gateway?
    - Answer: Best practices include using HTTPS, implementing authentication and authorization, enabling logging, and conducting regular security audits.

1. How do you perform a security audit on APIs in API Gateway?
    - Answer: A security audit can involve reviewing IAM policies, examining access logs, testing for vulnerabilities, and ensuring compliance with security best practices.

1. What is the importance of rate limiting in API Gateway?
    - Answer: Rate limiting helps prevent abuse of APIs, ensuring fair use among consumers and protecting backend services from being overwhelmed.

## Scenario-Based Questions
1. In your project, why did you place API Gateway in front of your Lambda functions? Why not just invoke the Lambda directly?
    - The Answer: We used API Gateway to decouple the client from the backend logic and provide a secure public endpoint.
    - Simple Explanation: Invoking Lambda directly requires AWS credentials (IAM). Our external data providers (like a third-party vendor sending us webhooks) don't have AWS users in our account. API Gateway provides a standard HTTP URL (like api.my-site.com/ingest) that they can hit safely.
    - Key Features: It also handles traffic management. If the vendor sends too much data at once, API Gateway can throttle requests so our Lambda doesn't crash.

1. What is the difference between an 'API Gateway Proxy Integration' and a 'Non-Proxy Integration'?
    - The Answer: This determines how much work API Gateway does versus the backend.
    - Lambda Proxy (Most Common): API Gateway acts as a simple pass-through. It sends the entire raw HTTP request (headers, body, query params) to Lambda as a massive JSON object. The Lambda must parse it.
        - Pros: Easiest to set up; full control in code.
    - Non-Proxy (Data Transformation): API Gateway transforms the data before sending it to the backend. We can use 'Mapping Templates' (VTL) to strip out unnecessary headers or rename fields.
        - Pros: Keeps the backend code cleaner; can integrate directly with AWS services (like writing straight to Kinesis) without Lambda.

1. We need to ingest data from a partner who sends us JSON files via a webhook. How do you set that up?
    - The Answer: I would create a POST method in API Gateway.
        1. Endpoint: Create a resource like /webhook.
        1. Security: Generate an API Key for the partner so we can track their usage and revoke access if needed.
        1. Backend: Point the integration to a Lambda function (to validate and store the JSON) or directly to an SQS Queue (to buffer the data if the volume is high).
        1. Response: Return a simple `200 OK` immediately so the partner knows we received the payload.

1. You mentioned using API Gateway to put data INTO the cloud. Can you use it to serve data OUT? How would you handle performance if thousands of users query the same report?
    - The Answer: Yes, we use it for 'Data as a Service'. To handle high read traffic, I would enable API Gateway Caching.
    - The Problem: If 1,000 users ask for 'Daily Sales Report', triggering 1,000 Lambda runs and 1,000 SQL queries is slow and expensive.
    - The Solution: We enable caching for a specific Time-to-Live (TTL), say 5 minutes.
    - How it works:
        1. User 1 requests report -> Lambda runs -> API Gateway stores result in cache -> Returns data.
        1. Users 2 to 1,000 request report -> API Gateway serves from cache instantly. Lambda is not touched.
    - Benefit: drastically reduces latency and database load.

1. We want to ingest clickstream data directly into Kinesis. Do we need a Lambda function in the middle?
    - The Answer: No, and removing Lambda is actually a best practice for high-throughput ingestion to save costs.
    - The Pattern: AWS Service Proxy.
    - How it works: We configure API Gateway to integrate directly with the Kinesis PutRecord API.
    - Configuration:
        1. Create an IAM Role that allows API Gateway to write to Kinesis.
        1. Use a VTL Mapping Template in API Gateway to map the incoming JSON body to the Kinesis payload format.
    - Benefit: This removes the 'Lambda Tax' (cold starts and execution duration costs), making the ingestion pipeline faster and cheaper.

1. How do you handle 'Throttling'? What happens if a client spams your API?
    - The Answer: We use Usage Plans and Throttling Limits to protect our downstream systems.
    - Token Bucket Algorithm: Imagine a bucket that holds 1,000 tokens. Every request takes a token. The bucket refills at a rate of 500 tokens/second. If the bucket is empty, the API returns a 429 Too Many Requests error.
    - Levels of Throttling:
        - Account Level: Protects the whole AWS account.
        - Stage Level: Protects a specific environment (Prod vs Dev).
        - Client Level: We give a specific API Key to a client and limit them to say, 100 requests/second, ensuring one noisy tenant doesn't bring down the system for everyone else.

1. We are exposing sensitive financial data via this API. How do we ensure only authorized employees can access it? An API Key isn't enough.
    - The Answer: Correct, **API Keys are for identification, not security**. For real security, we use Authorizers.
    - Option A: Amazon Cognito User Pools: If we have a mobile/web app. Users log in, get a JWT (JSON Web Token), and send it in the header. API Gateway validates the token automatically.
    - Option B: Lambda Authorizer (Custom): Best for B2B scenarios. We write a small Lambda function that takes the incoming token (or OAuth header), validates it against our own database or LDAP, and returns an IAM policy saying 'Allow' or 'Deny'.
    - Why: This offloads security logic from the main backend Lambda. The main Lambda only runs if the Authorizer says 'Yes'.

1. Our data warehouse (Redshift) is in a private VPC. How can API Gateway (which is a public service) query Redshift without exposing Redshift to the internet?
    - The Answer: We use API Gateway Private Integrations via VPC Links.
    - The Architecture:
        1. Network Load Balancer (NLB): We place an internal NLB inside the private VPC sitting in front of the data service (e.g., an EC2 or ECS container that queries Redshift).
        1. VPC Link: We create a VPC Link in API Gateway that connects securely to that NLB.
    - The Flow: Public Internet -> API Gateway -> (Secure Tunnel/VPC Link) -> NLB (Private) -> Redshift.
    - Result: The data remains in the private network, but authorized API users can request it safely.

1. You are seeing a 504 Gateway Timeout error. The downstream Lambda is running successfully in the logs, but the API client sees a failure. What is happening?
    - The Answer: This is a classic Hard Timeout Limit issue.
    - The Constraint: API Gateway has a strict maximum timeout of 29 seconds. It cannot be increased.
    - The Mismatch: Lambda allows a timeout up to 15 minutes.
    - The Scenario: If the Lambda job takes 45 seconds to process a complex ETL calculation:
        1. API Gateway waits for 29s, gives up, cuts the connection, and returns 504 to the user.
        1. The Lambda continues running in the background for another 16s and finishes 'successfully' in CloudWatch logs.
    - The Fix:
        1. Optimize the query to run faster than 29s.
        1. Asynchronous Pattern: Change the API to return a `202 Accepted` immediately, trigger the Lambda asynchronously, and provide a 'status check' endpoint for the user to poll later.

1. You have an API in Production and one in Development. How do you manage these environments without creating two separate API Gateways?
    - The Answer: We use API Gateway Stages.
    - Simple Explanation: A 'Stage' is like a snapshot of our API. We can have a dev stage and a prod stage pointing to the same underlying API definition but triggering different backend Lambdas.
    - Configuration: We use Stage Variables.
        - In the prod stage, the variable lambda_alias = PROD.
        - In the dev stage, lambda_alias = DEV.
    - Benefit: We only manage one API structure. When we deploy, we just choose which 'stage' to update. It keeps our infrastructure clean.

1. A user reports the API is failing, but you can't reproduce it. How do you debug this?
    - The Answer: I would check the CloudWatch Execution Logs (not just the Access Logs).
    - Access Logs: Tell us who hit the API and the status code (e.g., 500).
    - Execution Logs: Tell us what happened inside. It shows the full trace: 'Method Request' -> 'Auth' -> 'Integration Request' -> 'Lambda' -> 'Response'.
    - The Fix: Usually, the execution log reveals the error, like 'Malformed Lambda Proxy Response' (meaning the Lambda returned bad JSON) or a 'Permission Denied' error accessing a downstream resource.

1. We need to build a live stock price dashboard. Polling the API every second is too expensive. What is the alternative?
    - The Answer: We should use API Gateway WebSocket APIs.
    - The Shift: Instead of the client asking 'Do you have new data?' every second (HTTP Request/Response), we open a two-way persistent connection.
    - The Flow:
        1. Client connects via WebSocket (wss://...).
        1. We store the ConnectionID in DynamoDB.
        1. When our backend ingestion system (e.g., Kinesis) detects a new stock price, a Lambda triggers, looks up the active ConnectionIDs, and pushes the data to the connected clients.
    - Benefit: This is true real-time streaming with lower latency and less network overhead.

1. We are deploying a major change to our Ingestion API. If it breaks, our entire data pipeline stops. How do we deploy safely?
    - The Answer: We use Canary Deployments.
    - How it works: We don't flip the switch for 100% of traffic at once.
    - The Setup: We configure the deployment to send only 10% of the incoming traffic to the new version (Canary) and keep 90% on the old stable version.
    - Validation: We monitor the error rates in CloudWatch for that 10%.
        - If Stable: We promote the release to 100%.
        - If Errors Spike: We rollback instantly. The 90% of users were never affected.

1. How do you protect your data ingestion API from malicious attacks like SQL Injection or DDoS, beyond just rate limiting?
    - The Answer: We integrate AWS Web Application Firewall (WAF) directly with API Gateway.
    - The Defense: WAF sits in front of the API.
    - Rules: We can create rules to block requests that contain:
        - Common SQL injection patterns in the JSON body.
        - Cross-site scripting (XSS) vectors.
        - Traffic from blacklisted IP addresses or specific countries (Geo-blocking).
    - Real World Scenario: If we see a sudden spike of 403 errors from a specific botnet, WAF can automatically update to block that IP range, protecting our backend Lambda from even waking up.

1. We need to upload profile images (binary data) along with user data through the API. How do you handle this?
    - The Answer: Handling binary in API Gateway requires specific configuration because it is text-native (JSON) by default.
    - Configuration:
        - Binary Media Types: We must explicitly add image/png or multipart/form-data to the API's settings.
        - Base64 Encoding: The client usually sends the image as a Base64 encoded string, or if sent as raw binary, API Gateway will encode it before sending it to Lambda.
    - Important Constraint: API Gateway has a payload limit of 10MB.
        - Better Architecture: For large files, we shouldn't pass them through the API. Instead, the API should return a S3 Presigned URL, and the client uploads the heavy image directly to S3. This saves cost and avoids timeouts.

## Error-Based Questions
1. You created a simple API Gateway that triggers a Lambda function to write data to DynamoDB. The Lambda runs successfully (you checked the logs), but the API Gateway returns a 502 Bad Gateway error to the client. Why?
    - The Answer: This is a Lambda Proxy Integration Contract violation.
    - The Cause: When 'Use Lambda Proxy integration' is enabled, API Gateway expects the Lambda to return a response in a very specific JSON format.
    - The Error: Your Lambda likely returned a simple string like Success or a plain dictionary.
    - The Fix: The Lambda must return a JSON object with at least `statusCode` and body:
        ```
        # Correct Return Format
        return {
            statusCode: 200,
            body: json.dumps({message: Data Ingested})
        }
        ```
        - If you miss this structure, API Gateway doesn't know how to map the response and throws a 502.

1. We are launching a marketing campaign. We expect 5,000 requests per second (RPS) to hit our data collection API. Our account limit is 10,000 RPS, but clients are getting 429 Too Many Requests at only 2,000 RPS. Why?
    - The Answer: You are hitting a Stage Level or Method Level throttle, not the Account limit.
    - The Hierarchy: AWS enforces throttling at three levels:
        - Account Level: The hard cap (e.g., 10k RPS).
        - Stage Level: Default is often lower (e.g., 1k or 2k) to protect other APIs.
        - Usage Plan Level: Limits specific API keys.
    - The Fix: Check the 'Default Method Throttling' setting in the API Gateway Stage Editor and increase it to match the expected load, or implement a Queue (SQS) behind the API to buffer the spike.

1. Your API triggers a Lambda that runs a 45-second SQL query on Snowflake. The Lambda finishes successfully, but the API client always receives a `504 Gateway Timeout`. Why?
    - The Answer: You hit the API Gateway Hard Timeout.
    - The Constraint: API Gateway has a strict maximum timeout of 29 seconds. This cannot be increased. Even if your Lambda can run for 15 minutes, API Gateway hangs up after 29s.
    - The Fix: You must switch to an Asynchronous Pattern.
        1. API Gateway triggers Lambda and immediately returns `202 Accepted` to the client.
        1. The Lambda continues running in the background.
        1. (Optional) The client polls a status endpoint or waits for a webhook when the job is done.

1. You built an API for vendors to upload bulk CSV data files. It works for small files, but when they try to upload a 20MB file, it fails immediately with a message about payload size. How do you fix this?
    - The Answer: API Gateway has a 10MB Payload Limit. You cannot upload large files directly through it.
    - The Solution: Use the S3 Presigned URL Pattern.
        1. The Client calls the API with metadata (filename, size).
        1. Lambda generates a Presigned S3 URL (a temporary, secure upload link) and returns it to the client.
        1. The Client uploads the 20MB file directly to S3 using that link, bypassing API Gateway entirely.
    - Benefit: This is cheaper and faster as the heavy data traffic doesn't pass through the API layer.

1. You are designing a high-throughput clickstream ingestion pipeline (100k events/sec). Current Design: API Gateway -> Lambda -> Kinesis. The Lambda costs are enormous. How do you optimize this?
    - The Answer: Remove the Lambda. Use API Gateway Direct Integration with Kinesis.
    - The Architecture: API Gateway can write directly to Kinesis Data Streams using a VTL (Velocity Template Language) mapping template.
    - The Logic: We map the incoming JSON body directly to the Kinesis PutRecord API format in the API Gateway configuration.
    - Benefit: We eliminate the 'Compute' layer entirely. We save the cost of 100k Lambda invocations per second and reduce latency by one hop.

1. Your API is throwing `500 Internal Server Error`. You rush to CloudWatch to see the execution logs, but the Log Group is empty. You checked the Stage settings, and 'Enable Access Logging' is definitely turned ON. Why are there no logs?
    - The Answer: You missed the Global Account-Level IAM Role.
    - The Cause: API Gateway is a service that runs outside your VPC. To write to your CloudWatch Logs, it needs permission to assume a role.
    - The Trap: Enabling logging in the Stage/Console is not enough. You must go to the main API Gateway Settings (Account level) and attach a generic IAM Role with `logs:CreateLogGroup` and `logs:PutLogEvents`.
    - The Fix: Create the role, add the ARN in the settings, and wait a minute. The logs will start appearing.

1. You built an API to upload JPEG profile pictures. The upload works, but when you download the image from S3 later, it is corrupted or unreadable. The file size looks slightly different than the original. Why?
    - The Answer: This is a Binary Media Type configuration error.
    - The Mechanics: By default, API Gateway treats all payloads as Text (UTF-8). When it receives a JPEG (binary), it tries to encode those bytes as text, which corrupts the data structure.
    - The Fix:
        1. Go to API Settings -> Binary Media Types.
        1. Add image/jpeg (or */*) to the list.
        1. Crucial Step: In the Client Request, ensure the Accept and Content-Type headers match image/jpeg.
    - Note: If using Lambda Proxy, you also need to handle Base64 decoding inside the Lambda code.

1. Your API is public (no Auth). Suddenly, valid users from a specific country (e.g., Brazil) report getting 403 Forbidden. You checked API Gateway Resource Policies, and there are no Deny rules. Who is blocking them?
    - The Answer: This is likely the AWS Web Application Firewall (WAF) attached to the API.
    - The Layer: WAF sits in front of API Gateway.
    - The Cause: Someone likely configured a Geo-Match Rule to block traffic from specific countries to reduce spam, or a Rate-Based Rule triggered because users behind a shared NAT in Brazil hit the request limit.
    - The Debug: Check the WAF Sampled Requests console, not the API Gateway logs. It will show the specific rule (e.g., Block-High-Risk-Geo) that matched.

1. You are building a Zero-Trust API for a bank. You configured Mutual TLS (mTLS) so clients must present a certificate. The client sends a valid certificate signed by your CA. However, the connection fails with `OpenSSL Error` or `Connection Reset` before even reaching API Gateway. Route53 and the Custom Domain are set up.
    - The Answer: This is a Trust Store or Domain Name ownership mismatch.
    - The Cause: mTLS happens at the handshake layer.
    - Check 1: Did you upload the correct Trust Store (PEM/JKS) to API Gateway custom domain settings?
    - Check 2: (The Expert Catch) Does the Client Certificate's Common Name (CN) or SAN match the Custom Domain Name? AWS checks this validation strictly.
    - The Fix: Verify the client cert chain against the Trust Store in S3 and ensure the CN matches the API endpoint.

1. Your Data Team is in London (eu-west-2). Your API Gateway is in London. Users in London complain that the API feels 'sluggish' (high latency). You check the configuration, and the Endpoint Type is Edge-Optimized. Why is 'Edge-Optimized' slower for local users?
    - The Answer: Edge-Optimized uses CloudFront points of presence globally.
    - The Path: Even though the user is in London and the server is in London, the request might go: User -> CloudFront Edge (London) -> AWS Backbone -> API Gateway (London).
    - The Overhead: This adds a 'double hop' and extra TLS termination overhead which is unnecessary for local traffic.
    - The Fix: Switch the Endpoint Type to Regional. This allows London users to connect directly to the API Gateway in the London region, removing the CloudFront hop.
